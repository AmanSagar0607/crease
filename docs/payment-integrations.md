# Stripe payment foundation (sandbox verification pending)

This is an initial server-side adapter, not a production-verified integration. A local test using actual Stripe sandbox webhooks recorded one USD 12.00 payment and a USD 3.00 partial refund correctly. Synthetic signature and database tests also pass. This narrow test does not establish complete provider support or production readiness; run broader sandbox and reconciliation tests before relying on it. No frontend connection flow, payment reporting, customer-to-visitor linkage, provider account validation, or automated reconciliation is implemented. There is no currency conversion and no revenue claim.

## Configuration

Set a dedicated `PAYMENT_ENCRYPTION_KEY` to a Fernet key (generate with `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`). Keep it private, back it up securely, and do not reuse an OAuth-token key. Rotating it requires re-encrypting existing secrets or disconnecting and reconnecting integrations. Configure `PUBLIC_API_URL` to the externally reachable HTTPS Crease API origin. Deploy migration `0004_payment_foundation` separately after the normal backup and test procedure; never run migrations automatically.

An authenticated project owner can POST to `/api/projects/{project_id}/payment-integrations/stripe` with `{"signing_secret":"whsec_...","live_mode":false}` using the existing same-origin session. The response supplies an endpoint URL; register it with Stripe and subscribe to `charge.succeeded`, `charge.captured`, and `charge.refunded`. Store the endpoint signing secret, not a Stripe secret API key. The endpoint verifies the original request bytes and signature using the official Stripe SDK, including its replay tolerance, before processing. The integration's test/live mode must match the webhook event. A status GET at the same project path reports whether an authenticated event arrived; it does not prove reconciliation. A DELETE removes the encrypted secret and webhook event IDs but preserves existing payment records. Also disable or delete the endpoint in Stripe: Crease cannot revoke it remotely.

Stripe events can arrive out of order or be retried. Event IDs are idempotent within an integration; captured charges use the charge ID as the transaction key. Cumulative refunded amounts can only increase. Conflicting captured amounts or currencies return 409 for manual investigation instead of silently overwriting. The implementation rejects events with invalid signatures or mode, ignores unsupported and uncaptured events, and stores integer minor units separately by currency and mode. Refund-before-charge is handled when the refund notification contains a captured charge snapshot. Events beyond the project's retention window do not recreate expired payment records. Verify provider support for subscriptions, asynchronous payment methods, disputes, partial captures, historical reconciliation and the relevant account configuration before use; these cases are not yet comprehensively supported.

Payment records are not linked to visitors or customers by this release. Any metadata in the webhook is deliberately ignored for attribution. Unmatched revenue must remain unattributed. The API does not accept browser-created payment events as proof. No card numbers or raw webhook bodies are stored. Stripe customer IDs are retained when provided. Project deletion removes payment records; scheduled retention removes old payments and webhook event IDs. Preserve backups under an explicit retention policy.
