# Revenue-first dashboard: overview

`GET /api/projects/{project_id}/overview?start=YYYY-MM-DD&end=YYYY-MM-DD&model=first_touch` requires an authenticated project owner. Dates are inclusive UTC calendar days, limited to 90 days; future end dates and invalid models are rejected. The previous period has equal length immediately before the selected period. Supported models are `first_touch`, `last_touch`, and `last_non_direct`. Existing acquisition API remains unchanged.

Visitors are distinct non-null visitor IDs with events in the period. Pageviews count pageview events; sessions count server-assigned sessions starting in the period. New means first observed within retained project event history during the period; returning means observed before it. Retention, consent, and identifier changes limit these figures. Daily series compare equal-offset days from the preceding period.

Acquisition and campaigns assign retained observed touchpoints using the selected model for visitors with a touchpoint during the period. Sources without evidence are Direct or unknown; medium and campaign may be Unknown. Session counts represent sessions started during the period by those visitors and use the selected visitor-level touchpoint, not per-session attribution. Landing pages count session entry paths, sessions, and distinct visitor IDs for sessions started in the period. Recent activity returns event name, path, and timestamp only; no event properties. Refer to ACQUISITION_REPORT.md for attribution limitations.

The optional `conversion_event` query parameter selects an exact event name. Conversions count distinct visitor IDs with that event in the selected period, not event occurrences; conversion rate is converted visitors divided by visitors. Acquisition and campaign rows count those converted visitors according to the selected visitor-level touchpoint; that touchpoint may occur after the conversion and is not proof of causality. Landing pages count distinct visitors who converted in a session that started on that entry page during the period. A visitor can appear in multiple landing-page rows. Events lacking visitor IDs cannot be counted. The selection is temporary and resets on navigation/project change; saved goals are not implemented. No selection returns null, distinct from a selected event with zero results. Revenue is unavailable and no zero amount is inferred. Campaign detail navigation is not implemented. The selected UTC dates also apply to the existing summary, event list, and funnel using optional `start` and `end` parameters. Their property filter remains separate from the overview and is disclosed there. Page analytics is available even for an empty project. Project timezones, saved conversion goals and detailed campaign navigation remain future work.

No schema migration is introduced. Do not run production migrations or deploy as part of this change.

Acquisition source search filters the up-to-50 source groups returned by the overview API. CSV export downloads matching groups with spreadsheet formula protection; conversion rates are decimal fractions and unavailable values are blank. The export is limited to those returned groups and is not a complete dataset export.

## Frontend redesign (local only)

The dashboard now presents reporting as one project-scoped product surface. A single shared toolbar owns the UTC preset or custom range, attribution model, conversion event and refresh, and Overview, Acquisition, Campaigns and Pages all read the same `GET /overview` response. Acquisition can fetch the immediately preceding equal-length window on demand when "Compare previous period" is enabled; that comparison is a second request, not a server-side join.

Acquisition tables sort, paginate 15 rows at a time, search locally over the returned groups and export formula-safe CSV. Campaign "Inspect" moves to Acquisition with the campaign prefilled in the search box. Pages shows top pages from the summary API, landing pages from the overview report, and the existing traffic explorer. Search boxes only filter what the API returned; they do not query the full dataset.

Sections whose APIs do not exist (User journeys, Revenue, Customers) are marked "Soon" in navigation and render an unavailable state listing the missing endpoints. No revenue or customer figures are inferred, and the revenue card continues to state that browser events are never treated as revenue. Live activity polls `GET /events` every 15 seconds while the section is open and discloses that it is a poll, not a stream. The funnel remains a two-step, session-ordered report with a visible limitation note.

No backend, schema, SDK or deployment change accompanies this redesign, and no production migration was run.
